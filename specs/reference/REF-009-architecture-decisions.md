# REF-009 — Architecture Decision Records (ADRs)

**Status:** Living reference specification — empty at project start, appended to throughout the project.

---

## 1. Purpose

Per MASTER_PROMPT.md Section 0 (Hard Rules): "When a low-level technical decision is not specified in the documentation ... you may choose a sensible, industry-standard, well-justified solution — but record the decision and its rationale [here] ... clearly label it as an implementation decision, distinct from a documented requirement." This file is that log. It also captures any deviation from the documented technology stack (only permitted with a justified technical reason, per the same Hard Rules section) and the MLflow-vs-W&B and similar "either/or" choices left open by the source documentation.

## 2. When to add an entry

Add an ADR here whenever:
- The source documentation is silent on a technical detail needed to implement a spec (e.g. exact Streamlit page layout, exact SQLite schema syntax, specific charting colour palette, choice between MLflow and Weights & Biases, choice between CSV and Parquet as the default processed format).
- An implementation genuinely required a documented deviation from a spec (Stage 7 of MASTER_PROMPT.md: "Update the relevant spec file if the implementation legitimately required a documented deviation").
- A reasonable industry-standard addition is made where the documentation is silent (e.g. the light logging addition noted in MASTER_PROMPT.md Section 9).

## 3. ADR template

```
### ADR-XXX — <short title>
- Date: YYYY-MM-DD
- Status: Proposed | Accepted | Superseded by ADR-YYY
- Context: <what decision was needed and why the documentation doesn't cover it>
- Decision: <what was decided>
- Alternatives considered: <list, with brief pros/cons>
- Rationale: <why this option>
- Affected specs: <DEV-XXX, REF-XXX>
```

### ADR-001 — Use Python 3.12 for the project virtual environment
- Date: 2026-08-15
- Status: Accepted
- Context: REF-008 specifies "Python 3.10+" without pinning an exact minor version. The machine's default `python` resolves to Python 3.14.0, which was released very recently; several pinned stack packages (TensorFlow/Keras, SHAP) do not yet reliably publish wheels for 3.14 on Windows. Python 3.12 was also available via the `py` launcher.
- Decision: Create `.venv` using Python 3.12 (`py -3.12 -m venv .venv`) rather than the default 3.14 interpreter.
- Alternatives considered: Python 3.14 (default; risk of missing/broken wheels for TensorFlow/SHAP); Python 3.10/3.11 (not installed on this machine, would require an extra install).
- Rationale: 3.12 satisfies the documented "3.10+" floor, has mature wheel support across the full pinned stack (notably TensorFlow 2.16.x, which supports up to 3.12), and was already available locally.
- Affected specs: DEV-001, REF-008.

### ADR-002 — Pin `pyarrow==15.0.2` instead of `16.1.0`
- Date: 2026-08-15
- Status: Accepted
- Context: `requirements.txt` initially pinned `pyarrow==16.1.0`. Installing the full stack failed dependency resolution: `mlflow==2.13.0` requires `pyarrow<16,>=4.0.0`, which conflicts with the 16.1.0 pin (streamlit only requires `pyarrow>=7.0`, so mlflow is the binding constraint).
- Decision: Pin `pyarrow==15.0.2` in `requirements.txt`, satisfying both mlflow's `<16` upper bound and streamlit's `>=7.0` lower bound.
- Alternatives considered: Downgrading mlflow (rejected — no version/technical reason to deviate from the documented "MLflow or W&B" choice once made); dropping the pyarrow pin entirely (rejected — Portability/Reproducibility NFR requires pinned versions, REF-004).
- Rationale: Smallest change that resolves the conflict while keeping every other pinned version from REF-008's stack intact.
- Affected specs: DEV-001, DEV-017, REF-008.

### ADR-003 — Import `torch` before `xgboost`/`scikit-learn` in every process (Windows DLL conflict)
- Date: 2026-08-15
- Status: Accepted
- Context: On this project's Windows 11 development machine, importing `xgboost`, `scikit-learn`, or even plain `pandas`/`numpy` before `torch` (which `sentence-transformers`/DEV-011 depends on) in the same Python process causes `torch` to fail with `OSError: [WinError 1114] A dynamic link library (DLL) initialization routine failed` when loading `torch/lib/c10.dll`. Reproduced reliably: `import xgboost; import torch` fails; `import sklearn; import torch` fails; `import pandas; import src` (which imports torch) fails; `import torch; import xgboost; import sklearn` succeeds, as does `import src; import pandas`. Root cause is a Windows-specific bundled-runtime-DLL conflict (numpy/xgboost/scikit-learn's bundled OpenMP runtime vs. torch's), not a project code defect. `KMP_DUPLICATE_LIB_OK=TRUE` did not resolve it; only import order does.
- Decision: `src/__init__.py` imports `torch` first, before anything else, wrapped in a `try/except ImportError`. Every module that does `import src` or `import src.<anything>` therefore gets the safe import order automatically. This matters most for DEV-013 (dashboard), which is the one process that will load both the XGBoost/SHAP path and the SBERT/torch path together.
- Alternatives considered: setting `KMP_DUPLICATE_LIB_OK=TRUE` (tested, did not fix this specific WinError); running SBERT and XGBoost in separate processes/services (rejected — adds architectural complexity/IPC that MASTER_PROMPT.md Section 0 explicitly warns against for this academic project); asking every script author to remember the correct import order manually (rejected — too fragile, easy to silently break).
- Rationale: A single, centralized fix in `src/__init__.py` is the smallest, most maintainable change that guarantees correct order everywhere without relying on developer discipline in every entrypoint script.
- Affected specs: DEV-001, DEV-008, DEV-009, DEV-011, DEV-013.

### ADR-004 — Pin `setuptools<81` for `mlflow` compatibility (`pkg_resources` removal)
- Date: 2026-08-15
- Status: Accepted
- Context: `mlflow==2.13.0` imports `pkg_resources` internally. Recent `setuptools` releases (>=81) no longer ship `pkg_resources` by default (deprecated, slated for removal), so a fresh `pip install` resolved a `setuptools` version that broke `import mlflow` with `ModuleNotFoundError: No module named 'pkg_resources'`.

- Alternatives considered: Upgrading mlflow past 2.13.0 (rejected without a version/technical reason to deviate from the already-made "MLflow" choice — would need its own ADR/justification and re-verification); installing the separate `pkg_resources`/`setuptools` compatibility shim package (rejected as an unnecessary extra dependency when pinning setuptools is simpler).
- Rationale: Smallest change that restores `pkg_resources` for mlflow while keeping the rest of the pinned stack (REF-008) unchanged.
- Affected specs: DEV-001, DEV-014, DEV-017, REF-008.

### ADR-005 — Treat "-" and "n/r" as missing (NaN), not zero, in DCS handbook tables
- Date: 2026-08-15
- Status: Accepted
- Context: DCS District Statistical Handbook tables (Table 9.3/9.4) use "-" for the overwhelming majority of blank cells and, in at least one observed case (Galle, Table 9.4, Commercial (Bus)/2020), the distinct marker "n/r" ("not reported"). Section 11 explicitly requires "investigate why the value is missing; do not automatically convert blanks to zero." Circumstantial evidence (Colombo's Three Wheeler registrations are "-" for 2019-2021 then nonzero for 2022-2023, consistent with Sri Lanka's real 2020-2022 vehicle import restriction period) is *consistent with* "-" meaning a genuine zero for at least some rows, but is not confirmation for every row/table/district.
- Decision: Both "-" and "n/r" are converted to NaN (missing), never 0, with a distinct `*_quality_note` value recorded per row ("reported_as_dash" vs. "not_reported" vs. "no_matching_source_row" for outer-join gaps) so the distinction is preserved and auditable rather than collapsed.
- Alternatives considered: Treating "-" as 0 (rejected - not confirmed for every row despite the Colombo three-wheeler circumstantial evidence; would violate Section 11's explicit rule without full investigation); treating both "-" and "n/r" identically (rejected - they are visibly different markers in the source and may carry different meanings, e.g. "not collected" vs. "nil").
- Rationale: The conservative, spec-compliant choice. XGBoost (DEV-008) handles missing values natively without requiring imputation, so leaving genuine ambiguity as NaN does not block modelling; DEV-005/DEV-006 can revisit per-feature imputation later with this decision as the documented starting point.
- Affected specs: DEV-004, DEV-005, DEV-006, REF-001.

### ADR-006 — Single canonical entry point for regenerating the processed dataset
- Date: 2026-08-15
- Status: Accepted
- Context: Discovered while implementing DEV-005: `src/data/clean_dataset.run()` unconditionally regenerates `data/processed/modelling_base_*.csv` from the raw interim data, and knows nothing about the DMT cross-validation flagging step (`src/data/validate_against_dmt.run()`, DEV-003 Section 10 step 6) that runs afterward. Any code path calling `clean_dataset.run()` alone (this happened in a test fixture) silently overwrites the processed file with a version missing the DMT flags, so the "final" file on disk could differ depending on which script or test last touched it - a real, order-dependent bug, not just a test-isolation nuisance, since DEV-005 (and everything downstream) reads this file as its input.
- Decision: Added `src/data/build_processed_dataset.py` with a single `build()` function that runs `clean_dataset.run()` then `validate_against_dmt.run()` in sequence. Every code path that regenerates the processed file (test fixtures included) must call this function, never `clean_dataset.run()` in isolation.
- Alternatives considered: Merging DMT validation directly into `clean_dataset.run()` (rejected - conflates two conceptually distinct steps owned by different specs, DEV-004 cleaning vs. DEV-003 Section 10 step 6 validation, into one function); documenting the correct call order and trusting callers to follow it (rejected - exactly what already failed once; too fragile).
- Rationale: A single, obvious entry point is the smallest fix that makes the correct order impossible to get wrong, while keeping `clean_dataset.py` and `validate_against_dmt.py` independently testable and conceptually separate.
- Affected specs: DEV-003, DEV-004, DEV-005.

### ADR-007 — Disclose, do not exclude, DCS/DMT-flagged rows in the frozen modelling dataset
- Date: 2026-08-15
- Status: Accepted
- Context: REF-006 Section 5.1 documents 100/375 rows (every district's Car 2019-2021 and Three-wheeler 2022 `new_registrations`) where district sums implausibly exceed the DMT national total, and explicitly defers the disposition decision ("exclude, down-weight, or simply disclose") to DEV-005/DEV-006. DEV-005 already carries the flag through unchanged (`data_quality_flag`) as a pass-through column. DEV-006 must decide what the *frozen, versioned* dataset that every model trains against actually does with these rows.
- Decision: Retain all 100 flagged rows in `data/processed/modelling_dataset_v1.csv` (neither excluded nor down-weighted at this stage), and additionally surface the flag on the *target* side: `target_data_quality_flag` carries the flag of the row that supplied `target_value` (the t+1 observation), since a row's own `data_quality_flag` describes its features, not necessarily the reliability of what it is being asked to predict. Both flags remain visible, queryable columns in the frozen dataset.
- Alternatives considered: Excluding flagged rows entirely (rejected - would remove ~27% of rows, disproportionately Car and Three-wheeler for several years, materially shrinking an already-thin 375-row dataset over a *reconciliation* discrepancy against a national total, not a proven per-district error; the DCS district-level figure itself may still be the more granular/authoritative source for a district-level model even where it disagrees with DMT); down-weighting via a sample-weight column now (rejected - premature to bake a specific weighting scheme into the frozen dataset before DEV-007/008 have even chosen a modelling approach; down-weighting remains available downstream since the flag is preserved).
- Rationale: Consistent with ADR-005's established conservative pattern on this project (preserve real, ambiguous observations with a visible flag rather than silently discard or correct them); keeps the disposition decision at the layer (DEV-007/008/012/013) that actually knows whether it needs to exclude/down-weight/simply disclose for its specific purpose, rather than deciding once for every future consumer.
- Affected specs: DEV-005, DEV-006, REF-001, REF-006.

### ADR-008 — Thin chronological split (2/1/1 target-years) keyed by `target_year`, not feature `year`
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-006's Error Case explicitly anticipates this: "Insufficient distinct time periods to form three genuinely separate chronological splits ... flag explicitly; do not force an artificial split that leaves validation/test with near-zero rows ... document the constraint and the accepted approach as an ADR." The real source coverage is 5 distinct years (2019-2023, yearly-only). Because the Fallback-path target is a next-period lead of `new_registrations` (`target_value` at year t = year t+1's observation), only 4 years (2019-2022) can carry a non-null target at all, and 2023 legitimately has none yet.
- Decision: Split boundaries in `configs/split_config.yaml` are keyed by `target_year` (the year being predicted), not the feature row's own `year`: train = target_year 2020-2021 (102 rows), validation = target_year 2022 (49 rows), test = target_year 2023 (47 rows). Rows whose target_year is 2024 (i.e. feature year 2023, no future observation yet) or whose target_value is null for any other reason (a genuinely missing t+1 source observation) are assigned `split = "unlabeled"` rather than forced into a bucket - 177 rows in the current dataset version.
- Alternatives considered: Keying the split by feature `year` instead of `target_year` (rejected - `target_year` is the period actually being evaluated/predicted, so keying the split boundary on it directly answers "what period does the test set evaluate performance on" (2023) without an off-by-one mental translation); a single train/test holdout with no validation split (rejected - DEV-008's 6-step process requires tuning on a validation period distinct from the untouched test period; even a thin 1-year validation period is preferable to conflating tuning and final evaluation); dropping years before 2020 or fabricating additional synthetic periods to widen the split (both rejected outright - Hard Rule against fabricated data, and dropping real, already-scarce observations for split convenience would contradict ADR-005/ADR-007's conservation approach).
- Rationale: The chosen boundaries are the maximum split that both (a) respects strict chronology (train ends before validation starts, which ends before test starts) and (b) keeps every split non-empty, given only 4 usable target-years. This is a data-driven consequence of the real, thin time series (REF-006 "Short annual time series" risk), not an engineering shortcut; DEV-014's evaluation report must caveat that validation/test each rest on a single target-year (49/47 rows respectively) when discussing metric stability.
- Affected specs: DEV-006, DEV-007, DEV-008, DEV-014, REF-006.

### ADR-009 — Frozen modelling dataset stored as CSV, versioned by content hash rather than date
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-006 FR4 gives `data/processed/modelling_dataset_v1.parquet` as an illustrative filename; REF-008/REF-009 both flag CSV-vs-Parquet as an open either/or choice this log should resolve. Separately, FR4 asks for a "version identifier (date/hash)" without specifying which.
- Decision: Write the frozen dataset as `data/processed/modelling_dataset_v1.csv` (matching the existing DEV-004/DEV-005 outputs, `modelling_base_2024.csv` and `modelling_features_2024.csv`), and derive the version identifier purely from a sha256 hash of the written file's bytes (`modelling_dataset_v1_<hash[:12]>`), not from the run date. `configs/split_config.yaml` additionally records the full `dataset_sha256` and a separate `frozen_date` (when this run happened), so the human-readable freeze date is still available without it being part of the identifier itself.
- Alternatives considered: Parquet (rejected for this stage - CSV keeps every processed-data artifact in this project human-diffable in git and consistent with the two files it directly extends; row count (375) is trivial for either format, so Parquet's storage/performance advantage doesn't apply here); a date-based version identifier, e.g. `modelling_dataset_v1_2026-08-15` (rejected - two runs on the same day produce indistinguishable identifiers even if the underlying data changed, and conversely a rerun on a *different* day with byte-identical output would wrongly appear to be a new version, undermining the DEV-017 reproducibility check "same dataset version + config reproduces same trained model").
- Rationale: A content hash gives the strongest possible guarantee that the identifier changes if and only if the data genuinely changed (FR4's own requirement, "must never be silently replaced ... without a new version identifier"), while CSV avoids introducing a second processed-data format into a project that has used CSV consistently so far without a prior justified need to switch.
- Affected specs: DEV-006, DEV-008, DEV-009, DEV-014, DEV-017, REF-008.

### ADR-010 — Implement the per-series linear trend baseline as specified, disclose its degeneracy rather than omit or fix it
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-007 FR3 asks for a "simple linear regression baseline where appropriate," giving "a linear trend fit per district/vehicle series on training-period data only" as an example. The frozen dataset's `train` split (REF-009 ADR-008) covers only 2 feature-years (2019-2020) per series. Checked against the real data: only 45/75 (60%) district x vehicle_type series have 2 distinct non-null training years at all (the minimum to fit a line), and those 45 are necessarily exact 2-point fits (zero residual degrees of freedom - the "fit" is just the observed 1-year change, not a statistically estimated trend). Once fit, this baseline produces physically impossible negative predictions (`new_registrations` cannot be negative) for 32/39 (82%) of validation predictions and 37/40 (93%) of test predictions - overwhelmingly because 2019-2020 sit just before Sri Lanka's real 2021-2022 vehicle-import-restriction collapse (see REF-006 Section 5.2, discovered while evaluating this baseline), so a 2-point line fit on pre-crash years extrapolates the pre-crash trend even further in the same direction, straight through zero.
- Decision: Implement the per-series linear trend baseline exactly as specified (fit on train-split rows only, per series, extrapolated to `target_year`), leave it null where fewer than 2 distinct non-null training years exist (never fabricated), and never clip negative predictions to zero. `evaluate_baselines()` additionally reports `n_negative_predictions` per split per baseline so this weakness is a visible, queryable number in `reports/baseline_metrics.json`, not a hidden footnote.
- Alternatives considered: Omitting the linear trend baseline entirely as "not appropriate" for this dataset (rejected - Section 23.1 lists it as one of three canonical baselines and DEV-007's Acceptance Criteria requires implementing it "where appropriate" with a documented decision, not silently dropping it; its poor performance is itself useful evidence for DEV-014's comparison, showing exactly how much a trend-extrapolation heuristic breaks down against a real regime shift); clipping negative predictions to zero (rejected - would silently alter a raw model output to look more plausible, contradicting the project's no-silent-correction pattern established in ADR-005/ADR-007); pooling all series into one global linear regression instead of per-series (rejected - FR3 gives per-series as its explicit example, and a pooled fit would hide exactly the per-series 2020-2022 collapse this dataset needs to surface, not the direction DEV-014's honesty requirement points toward).
- Rationale: The spec's "where appropriate" qualifier is satisfied by implementing the baseline faithfully and disclosing quantitatively why it is weak here (degenerate 2-point fits, majority-negative predictions), rather than by a judgment call to skip it - this keeps the three-baseline comparison in DEV-014 complete and honest, and the weakness itself is a documented, real finding about this dataset's usable training window, not a defect to hide.
- Affected specs: DEV-007, DEV-014, REF-006.

### ADR-011 — XGBoost feature set: exclude all-null features, one-hot encode vehicle_type, single combined model
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-008 FR ("14.1 Inputs") lists population/density, vehicle type, and time features as candidate inputs, to be read from `configs/feature_list.yaml` (DEV-005) rather than hardcoded. Six of that config's columns (`population`, `population_density`, `quarter`, `month_sin`, `month_cos`, `vehicles_per_1000_people`) are 100% null across every labeled (train/validation/test) row in the current dataset version (DEV-003 has not yet acquired population data; the dataset is yearly-only - see DEV-005/REF-001). Separately, `vehicle_type` is categorical and DEV-005 left open whether to train one combined model or separate per-vehicle-type models.
- Decision: (1) Numeric feature columns that are 100% null across every labeled row are automatically excluded from the actual training matrix (`drop_all_null_features()`), and the exclusion is recorded verbatim in the saved model's `metadata.json` (`excluded_all_null_features`) - the "exact feature list" persisted for reproducibility (Section 24) is what the model actually saw, not the full DEV-005 config list. (2) `vehicle_type` is one-hot encoded (`sklearn.preprocessing.OneHotEncoder`, fixed to the REF-002 canonical categories `[Motorcycle, Car, Three-wheeler]` so the encoded column set never depends on which categories a given split happens to contain) and used in a single combined model across all three vehicle types, per DEV-005's stated default. (3) The fitted encoder is persisted alongside the model (`models/xgboost_v1/onehot_encoder.joblib`) as the "preprocessing object" DEV-008's Data Requirements calls for.
- Alternatives considered: Passing all-null columns through anyway and letting XGBoost's native missing-value handling silently no-op on them (rejected - technically harmless to predictions, but would misrepresent "the exact feature list" in the model registry as including signal the model never actually had; also pollutes DEV-010's future SHAP output with zero-importance features that look like an oversight rather than a documented gap); native XGBoost categorical support (`enable_categorical=True`, xgboost >= 1.6) instead of one-hot encoding (rejected - one-hot encoding is the more standard, universally-understood choice for a 3-category variable, keeps the persisted model format simple, and avoids a categorical-dtype contract between training and every future inference caller); separate per-vehicle-type models (rejected without a strong reason to deviate from DEV-005's stated single-combined-model default, and would further shrink an already tiny per-series training set - each vehicle type only has ~34 labeled rows).
- Rationale: The exclusion rule is fully automatic and data-driven (re-evaluated every run against the actual labeled data), not a one-time hardcoded list, so it self-corrects once DEV-003 acquires population data or monthly granularity becomes available - at that point the previously-null columns will simply stop being excluded, with no code change required.
- Affected specs: DEV-005, DEV-006, DEV-008, DEV-010, DEV-014.

### ADR-012 — XGBoost tuning methodology: full grid search, validation-MAE selection, refit on train+validation before test
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-008 FR4/FR5 require tuning `n_estimators`, `learning_rate`, `max_depth`, `min_child_weight`, `subsample`, `colsample_bytree` "using only training/validation periods," then selecting on validation performance and reporting test performance once - without specifying the search strategy, the selection metric (MAE vs. RMSE vs. R²), or whether the finally-reported model is refit on train+validation before its one test-period evaluation.
- Decision: (1) Full grid search over `configs/model_params.yaml`'s `xgboost.tuning_search_space` (972 combinations), each fit on `train`-split rows only and scored on `validation`-split rows only - `tune_hyperparameters()` structurally has no test-period parameter at all, so leaking the test period into tuning is not just a discipline rule but impossible by the function's own signature. (2) Validation **MAE** is the selection metric (not RMSE or R²) because RMSE is dominated by the extreme-outlier districts from the real 2020-2022 collapse (REF-006 Section 5.2) - selecting on RMSE would effectively be selecting the hyperparameters that best fit a handful of huge-district rows, not overall predictive quality. (3) The selected hyperparameters are refit once on train+validation combined (151 rows) before the single test-period evaluation, maximizing the data available to the final production model while keeping the validation split's role strictly limited to hyperparameter selection (it is never touched again afterward).
- Alternatives considered: K-fold cross-validation instead of a single validation split (rejected outright - chronological order must be preserved per the Hard Rule against random splitting; k-fold would shuffle across time periods); RMSE or R² as the selection metric (rejected per the outlier-domination reasoning above; also R² is undefined/unstable with only 49 validation rows and several near-zero-variance subsets); NOT refitting on train+validation (i.e. reporting test metrics from the original train-only fit) (rejected - with only 102 training rows, discarding the 49 validation rows for the final production model wastes nearly a third of the already-small labeled dataset for no benefit, since validation's tuning role is already complete by that point).
- Rationale: Every choice here follows the same underlying principle - use the scarce labeled data (198 rows total) as fully as the Hard Rules allow without ever letting the test period influence anything upstream of its own one-time evaluation.
- Affected specs: DEV-007, DEV-008, DEV-014.

### ADR-013 — LSTM (DEV-009) skipped: real sequence density fails the documented conditionality gate
- Date: 2026-08-15
- Status: Accepted
- Context: Source doc Section 15 makes LSTM explicitly conditional: "Used to model sequential patterns when the final dataset contains enough observations per district/vehicle category; most meaningful with monthly or another dense resolution. If only a small number of yearly observations exist, treat LSTM results cautiously and possibly as an experimental comparison only." Section 15.1's sequence-construction method is written specifically for monthly data ("sliding window of previous 6 or 12 months"). `src/models/lstm_model.py::assess_sequence_density()` was built to check this against the real frozen dataset (`data/processed/modelling_dataset_v1.csv`) before any sequence/model code is written, per DEV-009's mandatory "Conditionality check (must run first)." Result: `month` is null for 100% of rows (the dataset is confirmed yearly-only, REF-001 Section 5) - the documented monthly construction does not apply at all. Even granting an undocumented reinterpretation of the window as yearly periods instead of months, a series needs `lstm.lookback_months` (configs/model_params.yaml, currently 6) + 1 = 7 consecutive non-null yearly observations to form even one (input-window, target) training pair; the dataset spans only 5 distinct years total (2019-2023), so the longest possible run for ANY series is 5, and the actual longest observed run across all 75 district x vehicle_type series is also 5. 0/75 series meet the 7-period threshold - not "insufficient," but categorically unreachable given the data's total time span.
- Decision: Do not build any sequence-construction, scaling, or LSTM training code beyond the assessment function itself. DEV-009's deliverable for this project state is the documented conditionality assessment (persisted to `reports/lstm_sequence_density_assessment.json`, regenerable by rerunning `src/models/lstm_model.py::run()`) concluding `"skip"`, not a forced "experimental" model. XGBoost (DEV-008) remains the sole production model; DEV-012/DEV-013 proceed on the XGBoost path per DEV-PLAN.md Section 2, unblocked.
- Alternatives considered: Building a "clearly labelled experimental" LSTM anyway, since Section 15's own wording allows for it (rejected - Section 15's "experimental comparison" language presumes *some* real sequence exists to compare, however thin; here 0/75 series can even form a single (window, target) pair at the documented minimum lookback, so there is no sequence to build without either fabricating periods (an explicit Hard Rule violation) or shrinking the lookback so far below the documented 6-12 range that the resulting "sequence" would be indistinguishable from - and no more informative than - DEV-007's already-implemented, already-weak linear-trend baseline (REF-009 ADR-010); this would be technically-present but scientifically empty, which DEV-009's own Business Rule and this session's explicit instructions rule out: "do not force an artificial LSTM implementation merely to satisfy the technology list"); reinterpreting "6 or 12 months" as "6 or 12 years" and waiting for more annual data collection (rejected as a present-tense option - would require 7 years of a single dataset edition per district/vehicle series, i.e. multiple additional years of DCS handbook editions beyond what has been acquired, not something achievable within this project's data-acquisition scope); silently omitting LSTM from the documentation entirely (rejected outright - Hard Rule against silently dropping a documented ML component; this ADR plus DEV-009's own conditionality-check section is the required, non-silent alternative).
- Rationale: Per CLAUDE.md Section 21, "the original documented requirement" (Section 15's explicit conditionality) is preserved rather than overridden by convenience; per Section 19's project constraints, no synthetic/interpolated data is introduced merely to make a technology-list item appear implemented. This is a data-driven, legitimate outcome (DEV-009's own Definition of Done explicitly allows for it), not a shortfall in implementation effort.
- Affected specs: DEV-009, DEV-012, DEV-013, DEV-014 (comparison report must state XGBoost as the only model evaluated, with LSTM's absence explained by this ADR, not silently omitted), DEV-016 (viva material must be able to explain why LSTM was skipped, not just that it was), REF-003, REF-006.

### ADR-014 — Aggregate one-hot vehicle_type SHAP contributions into a single reported factor
- Date: 2026-08-15
- Status: Accepted
- Context: DEV-008 (REF-009 ADR-011) one-hot encodes `vehicle_type` into three model-input columns (`vehicle_type_Motorcycle`, `vehicle_type_Car`, `vehicle_type_Three-wheeler`). SHAP, by construction, attributes a separate value to each of the three dummy columns. DEV-010 FR ("17.2 Local explanations") expects output that supports a single human-readable sentence like "increased by strong recent registration growth ... while another feature slightly reduces the score" - three fragmentary vehicle_type_* values do not read as one factor a person can name.
- Decision: `src/explainability/shap_explainer.py` reports SHAP output at two levels: (1) a `raw_contributions`/`raw_feature_ranking` view with every individual model-input column, including all three `vehicle_type_*` dummies, unmodified - so nothing is silently truncated (DEV-010 Edge Case); and (2) an aggregated `contributions`/`aggregated_feature_ranking` view where the three dummies are collapsed into one `vehicle_type` entry per row, computed as the signed sum of the three dummy columns' SHAP values (the standard, mathematically correct way to collapse a one-hot group's SHAP attribution back to its original categorical feature, since exactly one dummy is "on" per row and the others' SHAP values reflect the "not this category" state relative to the same baseline).
- Alternatives considered: Reporting only the raw per-dummy values (rejected - fails DEV-010's own local-explanation sentence-support requirement, and would make `vehicle_type_Car`/`vehicle_type_Three-wheeler` look like separate, confusingly-named "features" to DEV-012/DEV-013's consumers); reporting only the aggregated value and discarding the per-dummy detail (rejected - violates the Edge Case rule that DEV-010 must never silently truncate, and would hide the genuine finding, discovered while implementing this, that the trained model's trees never actually split on `vehicle_type_Car` or `vehicle_type_Three-wheeler` at all (0.0 SHAP importance for both, confirmed via the booster's `get_score()`) - collapsing away the raw values would make that real, checkable model behavior invisible).
- Rationale: Reporting both levels serves both consumers - DEV-012's recommendation sentences need one named "vehicle_type" factor, while DEV-014's evaluation report and DEV-016's viva material benefit from being able to say precisely which one-hot dummy the model actually used.
- Affected specs: DEV-008, DEV-010, DEV-012, DEV-014.

### ADR-015 — Pin `tf-keras==2.16.0` to fix a SHAP + transformers (Keras 3) crash when both are imported in one process
- Date: 2026-08-15
- Status: Accepted
- Context: `shap.TreeExplainer.__init__` unconditionally probes whether the model being explained is a HuggingFace transformers language model (`is_transformers_lm()` -> `safe_isinstance(model, "transformers.TFPreTrainedModel")`). `safe_isinstance` only performs this probe if `transformers` is *already* present in `sys.modules` - harmless in isolation, but once anything in the same process has imported `sentence-transformers` (DEV-011, and therefore any process running both SHAP and SBERT together, e.g. the DEV-013 dashboard, or simply the shared pytest session where `tests/test_environment.py` imports the full pinned stack first), the probe's `getattr(transformers, "TFPreTrainedModel", None)` triggers `transformers`' lazy TensorFlow-integration submodule, which imports `tf_keras` if present or otherwise falls back to `keras` directly - and `tensorflow==2.16.1` bundles Keras 3 by default, which `transformers`' TF integration explicitly does not support ("Please install the backwards-compatible tf-keras package"), raising a `ValueError` at `shap.TreeExplainer()` construction. This is not a DEV-010 code defect: our model is a plain `xgboost.XGBRegressor`, never a transformers model - the crash is a side effect of an unrelated isinstance probe. Confirmed real (not test-artifact-only): this failure mode will recur in the DEV-013 dashboard process, which needs both SHAP and SBERT loaded together, so it had to be fixed at the dependency level now rather than deferred.
- Decision: Add `tf-keras==2.16.0` (matching `tensorflow==2.16.1`'s minor version, per `tf-keras`'s own versioning convention of tracking TensorFlow's minor release) to `requirements.txt`, installed with `--no-deps` to avoid re-triggering unrelated transitive-dependency drift. This satisfies `transformers`' TF-integration import path without changing any pinned model-relevant package (TensorFlow, Keras, NumPy, XGBoost, SHAP, scikit-learn all remain at their REF-008 pinned versions).
- Alternatives considered: Downgrading `tensorflow` to a pre-Keras-3 release (rejected - larger, unjustified deviation from the already-pinned REF-008 stack for a problem that has a smaller, targeted fix); monkeypatching around the `is_transformers_lm` check or catching the exception in `src/explainability/shap_explainer.py` (rejected - papers over a real, recurring environment gap rather than fixing it, and would need to be re-applied anywhere else in the codebase that constructs a `shap.TreeExplainer` in a process alongside `transformers`, e.g. DEV-013); leaving it unfixed on the theory that DEV-010's own test suite happened to pass in isolation (rejected outright - the failure is real and session/process-order-dependent, and the exact process shape it fails under (SHAP + transformers loaded together) is precisely what DEV-013 requires, not an edge case that can be deferred).
- Rationale: Smallest, most targeted change that resolves the actual root cause (a missing optional compatibility shim `transformers` itself asks for by name) without touching any package version that the rest of the pinned stack depends on.
- Affected specs: DEV-010, DEV-011, DEV-013, REF-008.

### ADR-017 — SBERT similarity_threshold retuned from 0.55 to 0.30; ambiguous_margin kept at 0.05
- Date: 2026-08-15
- Status: Accepted
- Context: `configs/sbert_categories.yaml` shipped with placeholder values (`similarity_threshold: 0.55`, `ambiguous_margin: 0.05`) explicitly marked "tune during DEV-011; log final value as an ADR if it deviates materially." A hand-written spot-check set (`tests/test_sbert_router.py`, matching DEV-011's own Testing Requirement) was run against the real `all-MiniLM-L6-v2` embeddings of the configured category descriptions, including the source doc's own Section 16.1 example query verbatim ("I repair motorcycles. Which district should I consider next month?").
- Decision: Lower `similarity_threshold` to **0.30**. Evidence: clearly relevant queries ("bike repair," "I fix motorcycles," "car mechanic here," "trishaw repairs," "tuk tuk mechanic") scored 0.55-0.73 top-category cosine similarity; clearly irrelevant queries ("what is the weather today," gibberish, an unrelated restaurant-recommendation request) scored 0.04-0.15. 0.30 sits with a comfortable margin above every irrelevant score observed and below every relevant score observed. `ambiguous_margin` is kept at the placeholder **0.05** - it correctly flagged a genuinely close two-category query ("I service scooters and mopeds," Motorcycle vs. Three-wheeler, margin 0.041) as ambiguous rather than silently picking the marginally-higher scorer, which is exactly its intended job.
- A known, accepted consequence: the source doc's own Section 16.1 example sentence, run verbatim through this configuration, comes back **"ambiguous"** (top score 0.423 for Motorcycle, margin 0.043 - just under the 0.05 margin) rather than "confident." This was a deliberate choice, not an oversight: loosening `ambiguous_margin` far enough to force that one specific sentence through as confident (down to ~0.04) would have been fitting the threshold to a single example rather than a principled cutoff, and would have let genuinely closer calls slip through unflagged. A system that occasionally asks a verbosely-phrased query to be clarified via the manual selector is the intended safe-fallback behavior (Business Rule), not a defect - Section 16.1 is a narrative illustration of the intended end-to-end flow, not a literal conformance test the implementation must force a "confident" verdict for.
- Alternatives considered: Rewriting the category description texts to produce cleaner separation (tried experimentally - shortening/de-overlapping the three descriptions changed which borderline queries were tight without clearly improving the canonical example's margin, and risked overfitting the wording to this one spot-check set rather than describing the categories accurately; reverted, original descriptions kept unchanged); keeping the 0.55 placeholder (rejected - would have classified 5 of 5 unambiguous single-category spot-check queries below threshold as "unsupported," including the source doc's own canonical example, which is a clear miscalibration against real query phrasing, not a defensible safety margin).
- Rationale: Threshold and margin are two independent, evidence-based gates, each retuned or confirmed against real embedding behavior rather than left as unvalidated placeholders, per the config file's own instruction.
- Affected specs: DEV-011, DEV-013.

### ADR-018 — Opportunity bands: per-vehicle-type train-split quartiles
- Date: 2026-08-15
- Status: Accepted
- Context: Section 18 step 4 explicitly leaves the exact thresholding mechanism open ("thresholds based on quantiles or a documented training-data rule"). `target_value` scales very differently by vehicle type (train-split medians: Motorcycle 664.5, Car 149.0, Three-wheeler 22.0 - REF-006 Section 5.2's collapse and general market-size differences both contribute), and a single `rank()` call always ranks districts within one selected vehicle category (Section 18 step 1: "the selected vehicle category").
- Decision: Opportunity bands (Low/Moderate/High/Very High) are assigned from **per-vehicle-type quartiles (25th/50th/75th percentile) of the `train`-split `target_value` distribution**, computed once when `RankingEngine.load()` runs and reused, unchanged, for every subsequent `rank()` call regardless of which period is requested (`src/recommendation/ranking_engine.py::compute_band_thresholds()`).
- Alternatives considered: A single global quartile set computed across all three vehicle types pooled together (rejected - Motorcycle's much larger absolute values would push nearly every Car/Three-wheeler district into "Low" regardless of its real standing within its own category, misrepresenting "relative service opportunity" for exactly the categories a Car or Three-wheeler mechanic would query); computing thresholds from the full dataset (train+validation+test+unlabeled) rather than train only (rejected - would let validation/test target values influence a threshold used to describe/report on those same periods, a soft form of the same leakage principle DEV-006/DEV-008 already enforce for model fitting, even though bands aren't a trained parameter per se); recomputing thresholds fresh from whichever districts are eligible for the specific requested period (rejected - explicitly against the Validation requirement "not recomputed ad hoc per query," and would make a "High" band mean a different absolute predicted value depending on which period happened to be queried, undermining comparability).
- Rationale: Train-split-only, per-vehicle-type, computed-once quartiles give a stable, leakage-safe, comparable band definition that matches how a query is actually scoped (one category at a time) and is trivially reproducible/testable (`tests/test_ranking_engine.py::test_band_thresholds_use_train_split_only_not_full_dataset`).
- Affected specs: DEV-012, DEV-013, DEV-014.

### ADR-025 — Source-priority rule for deduplicating district-year-vehicle_type-metric rows (retroactively logged)
- Date: 2026-08-15 (decision originally made and implemented during DEV-004; this entry was found missing during the DEV-015 test-suite audit and is logged now to close the gap - TODO.md Phase 3 had already marked "Decide and document the source-priority rule ... (log as ADR)" complete, but no corresponding REF-009 entry existed).
- Status: Accepted
- Context: `src/data/clean_dataset.py::deduplicate()` needs a rule for what to do when the same (district, year, vehicle_type, metric) key appears more than once in the raw extracted data - either because two different DCS handbook editions both cover that period, or because the same PDF table was parsed twice for the same edition (a real extraction artifact - observed once, Trincomalee 2019 Three-wheeler `new_registrations`).
- Decision: Two distinct cases, handled differently: (1) **Cross-edition duplicates** (same key, different `handbook_edition_year`) - the most recent edition wins, since a later handbook edition is presumed to supersede/correct an earlier one for the same historical period. (2) **Same-edition duplicates** (same key, same `handbook_edition_year`) - if both copies agree (`value_raw` identical), keep one (a harmless double-parse, not a real conflict); if they disagree, **exclude both** and log a loud warning identifying the exact key, rather than guessing which value is correct.
- Alternatives considered: Always keeping the first-encountered row regardless of edition (rejected - would arbitrarily prefer whichever row happened to be parsed first, with no principled basis, and would silently keep a potentially-outdated edition's figure over a corrected later one); silently averaging or picking the larger/smaller of two disagreeing same-edition values (rejected outright - Hard Rule against fabricating/guessing a value not actually present in the source; the correct value requires manual inspection of the source PDF, which excluding-and-logging enables without blocking the rest of the pipeline).
- Rationale: Cross-edition preference-for-recency is a defensible, standard provenance rule; same-edition disagreement is a genuine extraction ambiguity that has no algorithmically correct resolution, so exclusion-with-loud-logging is the only option consistent with the project's no-fabrication Hard Rule. Verified directly (not just via the end-to-end "no duplicate keys in final output" check) by `tests/test_clean_dataset_deduplicate.py`, added during the DEV-015 audit.
- Affected specs: DEV-004, DEV-015.

### ADR-029 — DEV-018 implementation: `email-validator` added; Flask/SQLAlchemy/Werkzeug/PyYAML/click promoted from transitive to explicit pins

- Date: 2026-08-21
- Status: Accepted
- Context: While implementing DEV-018, two gaps in the REF-010/ADR-027 stack addendum surfaced. (1) WTForms' `Email()` validator (used throughout `app/forms/auth.py`) raises immediately at validation time unless the separate `email_validator` package is installed — REF-010 did not anticipate this sub-dependency. (2) `Flask`, `SQLAlchemy`, `Werkzeug`, `PyYAML`, and `click` were all already present in the environment as *transitive* dependencies (Flask and SQLAlchemy via `mlflow`'s bundled tracking server; Werkzeug via Flask; PyYAML and click via several existing packages) but had no explicit pin in `requirements.txt`. `app/` now imports all five directly (`flask`, `sqlalchemy.event`/`Engine`, `werkzeug.security`, `yaml`, `click`), which is exactly the situation ADR-024 (scipy) already established a precedent for: a package used only incidentally by another dependency, now imported by first-party code, needs its own explicit pin so a future `pip install` can't silently resolve a different, unverified version for code that now depends on it directly.
- Decision: Add `email-validator==2.3.0` (confirmed to perform syntax-only validation, `check_deliverability=False` by WTForms' own default — no network/DNS calls occur during form validation). Add explicit pins for `Flask==3.1.3`, `SQLAlchemy==2.0.52`, `Werkzeug==3.1.8`, `PyYAML==6.0.3`, `click==8.4.2` — the exact versions already installed and verified working together with the rest of the pinned stack (confirmed via the full `pytest tests/` run in DEV-018's verification pass).
- Alternatives considered: Leaving these five unpinned, relying on `mlflow`'s/Flask's own transitive constraints (rejected — same reasoning as ADR-024: first-party code now imports them directly, so an implicit, potentially-drifting version is exactly the fragility the project's "exact dependencies" reproducibility requirement exists to prevent); a lighter hand-rolled email regex instead of WTForms' `Email()` validator plus `email_validator` (rejected — reinventing RFC-compliant-enough email validation is unnecessary complexity for a well-solved problem, and WTForms' validator is already the standard choice this project uses via Flask-WTF).
- Rationale: Closes a real gap discovered during implementation (the missing `email_validator` dependency would have broken every form on first real use) and extends ADR-024's already-established, narrowly-scoped "pin what first-party code imports directly" rule to the marketplace's own first-party code, without touching any ML-system package version.
- Affected specs: DEV-018, REF-010 (Section 2's stack table implicitly extended by this ADR).

### ADR-030 — DEV-019 implementation: auto-seed Service starter list at app startup; profile-completion redirect implemented in the shared login route

- Date: 2026-08-21
- Status: Accepted
- Context: Two implementation-level decisions were needed that REF-011/DEV-019 left open. (1) DEV-019 FR2 requires the `Service` table to carry a starter list "at DEV-019 implementation time," but not *how* that seeding is triggered on a fresh database. (2) DEV-019 FR3 requires a mechanic with no `MechanicProfile` to be "redirected there after login... until they save one" — but the only place "after login" can be observed is the shared login route, which DEV-018 already owns and which every role passes through identically.
- Decision: (1) `seed_default_services()` (`app/models/mechanic.py`) is called once from `create_app()`, immediately after `db.create_all()`, and is a no-op if any `Service` row already exists — so it runs safely on every app start (including every test's fresh in-memory database) without a separate manual setup step, and never overwrites an admin's later edits (DEV-022) once any row exists. (2) `app/routes/auth.py::login()` gained one additional branch, checked only for `role='mechanic'` users with no `mechanic_profile`: redirect straight to `mechanic.edit_profile`, ahead of any `next=` query parameter. Every other login path (customer, admin, and a mechanic who already has a profile) is unchanged.
- Alternatives considered: A separate `flask seed-services` CLI command mirroring `flask create-admin` (rejected — `Service` rows are reference/lookup data every deployment needs immediately to have a working form, unlike the admin account, which is deliberately a single, explicit, one-time provisioning act; requiring a manual step here would leave a fresh install's mechanic-profile form with an empty, useless services checklist by default); implementing the profile-completion redirect as a decorator applied to every mechanic-only route instead of a single login-time redirect (rejected — would fire repeatedly on every request rather than once at login, and would need to special-case the `edit_profile` route itself to avoid an infinite redirect loop, whereas a single check at the one moment "login succeeded" is simpler and matches the literal FR3 wording "after login... until they save one").
- Rationale: Both choices are the smallest change that satisfies the literal FR wording while keeping the seeding idempotent (safe to run unconditionally) and the redirect scoped to exactly the one event (login) the requirement names.
- Affected specs: DEV-018 (`app/routes/auth.py` extended — one existing test updated to match the new, intentional `/mechanic/profile` behavior, not weakened), DEV-019, REF-011 (Section 3.3).

### ADR-031 — DEV-020 implementation: EXISTS-based (`.any()`) filtering, service filtered by ID, rating sort falls back to name until DEV-021

- Date: 2026-08-21
- Status: Accepted
- Context: Three small implementation-level choices were needed that REF-011/DEV-020 left open at the literal-SQL level. (1) REF-011 Section 6 illustrates the district/vehicle-type/service filter combination as a single `LEFT JOIN ... GROUP BY` query, but its own text defers to "SQLAlchemy ORM queries... not raw SQL" for the actual implementation. (2) That same illustrative SQL binds a `:service_name` parameter, not an ID. (3) DEV-020 FR3/FR4 ask for "average rating descending, unrated after rated" sorting and display, but the `Review` table (REF-011 Section 3.6) does not exist yet — its creation is explicitly DEV-021 FR1's responsibility, not DEV-020's, and DEV-020 was explicitly instructed not to begin DEV-021 work.
- Decision: (1) `app/routes/marketplace.py::_search_mechanics()` filters via `MechanicProfile.vehicle_type_rows.any(...)` / `.services.any(...)` — SQLAlchemy relationship `.any()`, which compiles to an `EXISTS` subquery per filter — rather than reproducing the illustrative `LEFT JOIN + GROUP BY` shape literally. (2) The service filter's query-string value is a `Service.id` (`?service=3`), validated via `db.session.get(Service, id)`, not a name string. (3) Every mechanic currently renders a static "No ratings yet" (never a fabricated number), and result ordering falls back to `User.name` ascending — a stable, deterministic key — since every mechanic's real rating is identically absent right now, making "rated first" trivially satisfied by any order at all.
- Alternatives considered: Literally implementing the `LEFT JOIN` + `GROUP BY` shape from REF-011 Section 6 (rejected — would require deduplicating rows the `.any()` approach never produces in the first place, adding complexity for no behavioral difference); filtering services by name (rejected — REF-011 Section 3.3 already declares `Service.name` merely `unique`, not friendlier to filter by than the primary key, and the dropdown's `<option value=...>` naturally carries the ID already); building a minimal `Review` table now just to give `_search_mechanics()` something to `ORDER BY` (rejected outright — direct scope creep into DEV-021 FR1, explicitly disallowed for this implementation pass; would also mean shipping an unused, untested table ahead of the spec that actually owns and tests it).
- Rationale: (1)-(2) are the more idiomatic, equally-correct SQLAlchemy expression of REF-011's own filtering semantics. (3) is the only honest option available while respecting the DEV-020/DEV-021 boundary — a data-driven consequence of implementation sequencing, in the same spirit as the ML system's own documented data-availability gaps (e.g. REF-006), not a shortcut, and is flagged directly in DEV-020.md for DEV-021 to revisit.
- Affected specs: DEV-020, DEV-021 (must revisit `_search_mechanics()`'s `ORDER BY` and every "No ratings yet" placeholder once `Review` exists), REF-011 (Section 6, cross-referenced not amended).

### ADR-032 — DEV-021 implementation: `Review`'s unique constraint is unconditional, not scoped to `status='visible'`

- Date: 2026-08-21
- Status: Accepted
- Context: REF-011 Section 3.6 states the uniqueness rule as "at most one **visible-lifecycle** review per (customer_id, mechanic_id) pair," which could be read either as a plain, unconditional `UNIQUE(customer_id, mechanic_id)` constraint, or as a *partial* constraint that only applies while `status='visible'` (which would let a customer create a fresh new row after their previous one was admin-removed). DEV-021 FR1 itself just says "the `(customer_id, mechanic_id)` unique constraint," without qualifying it.
- Decision: A plain, unconditional `db.UniqueConstraint("customer_id", "mechanic_id")` — it applies to every `Review` row regardless of `status`. An admin-removed review permanently occupies its (customer, mechanic) slot; if a customer's review is later restored (`restore_review()`), it becomes visible again, but they cannot create an entirely separate second row for the same mechanic while an admin-removed one still exists.
- Alternatives considered: A partial/filtered unique index (`CREATE UNIQUE INDEX ... WHERE status='visible'`, achievable in SQLAlchemy via `Index(..., sqlite_where=...)`) so a fresh review becomes possible again after removal (rejected — meaningfully more complex for a case that isn't reachable at all yet, since DEV-022's admin UI that would ever set `status='removed_by_admin'` doesn't exist until the next spec; REF-004 Section 5's anti-over-engineering constraint favours the simpler constraint until a real need for the partial version is demonstrated).
- Rationale: The plain constraint is what DEV-021 FR1 literally asks for, is trivially expressed with SQLAlchemy's standard `UniqueConstraint`, and the scenario the more permissive alternative would help (a customer wanting a clean second attempt after moderation) is not yet reachable in this implementation phase in any case.
- Affected specs: DEV-021, DEV-022 (if a future need to "let a customer re-review after removal" is ever raised, it would revisit this ADR, not silently reinterpret the constraint), REF-011 (Section 3.6, cross-referenced not amended).

### ADR-033 — DEV-022 implementation: ORM-level cascade delete on both `User` relationships; admin accounts entirely excluded from management routes

- Date: 2026-08-21
- Status: Accepted
- Context: DEV-022 FR5 requires account deletion to cascade correctly ("deleting a `User` cascades to their `MechanicProfile`/`Review` rows"), and its Edge Cases section explicitly says the cascade behavior "must be decided and documented explicitly." Two things needed a concrete implementation: (1) how the cascade is actually achieved, given SQLite's `PRAGMA foreign_keys=ON` (DEV-018 ADR, REF-011 Section 2) rejects deleting a row that other rows still reference via FK, with no `ON DELETE CASCADE` clause defined at the DB level; and (2) DEV-022's own text repeatedly implies admin accounts are simply out of scope for this UI ("manage customer accounts," "manage mechanic accounts" — never "manage admin accounts"), but REF-012's authorization matrix didn't yet have a row ruling this out explicitly, so it needed an explicit decision, not an assumption.
- Decision: (1) `cascade="all, delete-orphan"` was added to both `User`-side relationship backrefs that DEV-022 needed: `MechanicProfile.user`'s backref (`user.mechanic_profile`) and `Review.customer`'s backref (`user.reviews_written`) — `Review.mechanic`'s backref already had this from DEV-021. With both in place, a single `db.session.delete(user); db.session.commit()` correctly cascades in every direction: a mechanic's `User` → `MechanicProfile` → `MechanicVehicleType`/`Service` associations/`Review` (mechanic-side), and a customer's `User` → their own written `Review` rows — verified empirically (a standalone script exercising both directions) before being relied on in `app/routes/admin.py`. (2) `admin.py::_get_manageable_user_or_404()` treats any `role='admin'` target — including the acting admin's own account — as not found, so no admin-management route can ever act on an admin account at all, structurally satisfying the Business Rule "an admin cannot block or delete their own admin account" (and, as a side effect, ruling out one admin acting on another, which REF-012's matrix now documents explicitly as its own row).
- Alternatives considered: Manually deleting dependent rows in the route function before deleting the `User` (rejected — the declarative cascade is the standard SQLAlchemy idiom for this, keeps the deletion rule co-located with the schema that defines it rather than scattered across whichever route happens to trigger a deletion, and is exercised identically regardless of *which* code path deletes a `User` in the future); relying only on a runtime `if user.id == current_user.id` check for self-protection without also excluding the `admin` role generally (rejected — the role-based exclusion is strictly stronger, and REF-012 never documented an "admin manages admin" capability in the first place, so allowing one admin to block a *different* admin would have been inventing scope, not preserving it).
- Rationale: The cascade lives in the model layer (the schema's own responsibility), verified once and reused by every future caller; the admin-role exclusion is both simpler and stronger than a purely self-referential guard, and keeps this spec's scope exactly matching FR-M14/FR-M15's literal "customer accounts"/"mechanic accounts" wording.
- Affected specs: DEV-022, REF-011 (Section 4's relationship list — cascade behavior is a schema-level property, cross-referenced here rather than restated), REF-012 (Section 3's matrix gained the "delete account" row this ADR documents the scope of).

### ADR-034 — DEV-023 implementation: lock-guarded lazy singleton for `RankingEngine`; no SBERT/NL-query box on this page

- Date: 2026-08-21
- Status: Accepted
- Context: DEV-023 FR6 requires the ranking engine to be "performed once per process and cached... rather than reloaded on every request," analogous to Streamlit's `@st.cache_resource`, but Flask has no equivalent decorator — a concrete mechanism was needed. Separately, the approved feature list's ML-components section (and DEV-023's own FR1) name XGBoost, `RankingEngine`, and SHAP as the components to reuse, but not SBERT — DEV-013's dashboard additionally offers a natural-language query box (routing free text to a category via `SBERTRouter`/`rank_from_query()`), and it needed an explicit decision whether Opportunity Insights should match that surface area or a narrower one.
- Decision: (1) `app/routes/insights.py` holds a module-level `_engine`/`_engine_load_error` pair, populated once via `RankingEngine.load()` inside `_get_ranking_engine()`, guarded by a `threading.Lock()` with double-checked locking so two near-simultaneous first requests can't both trigger a duplicate load (DEV-023's own Edge Case about concurrent mechanics). `src.recommendation.ranking_engine` is imported lazily, inside the function body, not at module load time — the entire XGBoost/SHAP/SBERT stack (and ADR-003's torch-first import-order requirement, transparently satisfied via `src/__init__.py` regardless of where the first `import src.*` happens) is therefore only ever loaded on the first real request to this one page, not at Flask app startup. (2) Opportunity Insights offers only the vehicle-type/period/top-N selectors `RankingEngine.rank()` itself takes — no natural-language query box, no `rank_from_query()`/`SBERTRouter` call. This is a deliberate, narrower surface than DEV-013's dashboard, matching DEV-023's own FR1 wording exactly ("calling ... `RankingEngine.rank(vehicle_type, period, top_n=...)`", not `rank_from_query`).
- Alternatives considered: Loading the engine eagerly at `create_app()` time (rejected — would force every marketplace request, including ones that never touch Insights, to pay the ~13-second XGBoost/SHAP/SBERT cold-load cost at process startup, or block the very first request of any kind; lazy loading confines that one-time cost to mechanics who actually visit this page); Flask's `g` (per-request) object instead of a module-level singleton (rejected — `g` is reset every request, which would defeat the entire point of caching an expensive, immutable, read-only resource); adding the same NL-query box as DEV-013 for feature parity (rejected without a documented requirement asking for it — DEV-023's FR list is deliberately narrower than DEV-013's, "a ranked list/table is sufficient for this page's purpose per the approved feature list, which does not ask for a second map" already established the same narrower-than-DEV-013 principle for the map; extending that same reasoning to the NL query box keeps this page's added surface area minimal and exactly spec-traceable).
- Rationale: The lock-guarded lazy singleton is the direct Flask analogue of `@st.cache_resource`, verified empirically (a real dev-server request measured ~12.7s cold, ~90ms warm; a dedicated test confirms `RankingEngine.load()` is invoked exactly once across three requests). Confining Insights to `rank()` alone keeps this integration exactly as narrow as DEV-023's FR list describes it, with the richer DEV-013 surface remaining available on the unmodified Streamlit dashboard for anyone who wants it.
- Affected specs: DEV-023, REF-003 (ML Component Architecture — SBERT remains DEV-013's own integration, unchanged).
